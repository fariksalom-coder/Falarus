# Привязка оплаты Rahmat к оператору

В мини-приложении вкладка «Rahmat»: найти действующий премиум аккаунт → выбрать конкретный подтверждённый платёж курса русского языка → загрузить JPG/PNG/WEBP/PDF до 8 МБ → отправить админу. Сумма, валюта, тариф и дата берутся из платежа. Оператор получает сообщение в боте о подаче заявки и решении администратора. Заявки доступны в его отчёте; администратор проверяет их в «Operatorlar va to‘lovlar» → «Rahmat sotuvlari».

Подтверждение меняет принадлежность существующей продажи оператору. Новые `payments`, договоры и подписки не создаются. В аналитике сохраняется ключ `p:<id>`, одна продажа и одно поступление; канал становится операторским, пометка «Rahmat» сохраняется. До подтверждения платёж остаётся автопродажей и не начисляет зарплату оператору. Проверка принадлежности — ответственность администратора: сам файл чека не доказывает участие оператора.

Зарплата использует существующие ставки и дневные бонусы. Один подтверждённый платёж даёт один курс, по исходной дате оплаты (Asia/Tashkent), даже если чек прислали позже. Подтверждение старого платежа пересчитывает соответствующий прошлый период. Последующие автоплатежи не наследуют оператора. При возврате платежа привязка остаётся в аудите, но продажа и зарплата исключаются из текущего расчёта; уже выплаченную зарплату приложение автоматически не возвращает.

Ограничения защищаются блокировкой платежа и уникальными индексами: один платёж имеет не более одной ожидающей или подтверждённой заявки; один файл не используется в двух таких заявках. Идентичная повторная отправка возвращает существующую заявку. Отклонённую заявку можно подать заново. При подтверждении повторно проверяются статус/канал/курс платежа и активность оператора. Чеки скачивает только администратор через существующую авторизацию, файлы хранятся в закрытом каталоге.

## Развёртывание

Сначала резервная копия БД, кода и uploads, затем аддитивная миграция `db/migrations/204_operator_rahmat_attribution.sql`, серверный код и новая frontend сборка. Если модуль операторов не установлен, миграция пропускает его: после установки `server/operator/schema.sql` миграцию 204 нужно выполнить снова. Обработчик Rahmat и существующие данные не изменяются. При откате кода новую таблицу следует сохранить для аудита; удаление не требуется.

## Проверка

`npm run lint`, `npm test`, `npm run build`. Интеграционный тест `tests/operatorRahmatClaims.test.ts` проходит реальные mini-app/admin/analytics маршруты на изолированном PostgreSQL-совместимом движке: авторизация Telegram, выбор допустимого платежа, файл, повторная отправка, конкурирующий оператор, отклонение, повторная заявка, подтверждение, зарплата и дата, возврат, неизменность премиума и общей выручки. Проверка внешнего вида на мобильном устройстве отдельно от API теста.
